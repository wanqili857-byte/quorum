## 最脆弱的一环（前三）

1. **「证据」列在真实用法下全灭**（`gates.py:189-194` × `templates/brief.md`）。工具的核心对冲手段是「明细逐条列原话 + 每条带我怎么查出来的」，而工单模板规定的表头正好让证据列解析不出来：真实产出的 65 条发现里带证据的 **0 条**，`--json` 契约里 25 条 source 的 `evidence` **0/25 非空**。作者的 demo 因为用了短表头而完全掩盖了这个洞。这一条不修，等于发布一个「承诺的证据列恒为空」的版本。
2. **「跨模型族一致 · 高置信」的性质与读者以为的不是一件事**，且它同时被两个独立缺陷放大：标签只数 family 字符串（随仓模板就把两个 primary 指到同一个 model），而混进簇里的错误归因只有一个 0.20 的相似度阈值在兜底——把错误措辞写得更接近正确措辞，告警就消失（实测 0.18→0.21，告警从「⚠️ 各家归因可能不同」变成「各家措辞接近」）。交叉审计的全部价值在这里，风险也全在这里。
3. **快照体系的三句保证都不成立**：基线共用 → 「三家审的是同一份材料」在单次 run 内不可判；全缺标记时的假绿 → 把「没有快照」印成「快照一致」；>8MB 首尾取样 → 「材料没变」在中段改动时静默失效。而 README 把这三句当作「设计上刻意做的选择」卖点。

## 附录 · 我推翻的既有结论

**A. 推翻工单自己的断言**

1. 工单 §2.A.5「大文件只按 (大小, mtime) 计入」——**不成立**。现实现是首尾各 64KB 取样哈希，且完全不使用 mtime（`snapshot.py:83-90`）。我实测 `_sample_hash` 与 `sha256(首64K+尾64K)` 十六进制完全相同。真正的洞是「中段字节不进指纹」，比工单描述更窄、也更难被发现。
2. 工单 §2.A.2 / `LESSONS.md:13` 的「四道内容门（体积 / 严重度标记 / 必需章节 / 非空）」——**实际只有三条判据**（`gates.py:56-57`），「严重度标记」只用于展示、从不参与判定，「非空」被「体积」吞掉。这就是工单自己定义的那类错误：门禁检查的性质不是读者以为的性质。
3. 工单 §2.B 引述的作者自述「对齐是启发式的、刻意保守——宁可拆细，不要合错」——**两个方向我都造出了反例，而且「合错」方向的触发成本更低**（同文件 + 泛泛措辞即可越过 0.07）；`cluster()` docstring 里「不同条 ≤0.06」的标定结论我无法复现（实测同一对无关发现随语料大小在 0.068–0.199 之间漂移）。
4. 工单 §2.B「同一家的两条永远不会合并——这个规则在什么情况下是错的」——**错在它按 reviewer 名而不是按结论身份**：同一个审核员把同一根因拆成两条、或把同一条发现写两遍，被保证永不合并（实测 2 簇「单家独有」），手工合并的负担转移给读者；反过来，两个 reviewer 名指向同一 channel+model（模板即是）却能合并成「高置信」——该规则只挡住了同名，没挡住同源。
5. `docs/LESSONS.md`「自检的 pattern 必须从规则表派生」与其事故**不对应**：事故的失效模式是「规则表缺项」，而实现的自检派生自扫描器**自己的**规则列表现状，缺项永远不可见（0 规则也全绿）。
