## 0. 背景（30 秒版）

作者做了一个**多模型交叉审计工具链**：让几个不同厂商的模型各自独立审同一份材料，
然后对齐它们的发现（一致 / 独有），并把复核处置台账里的「✅ 已修」变成**可执行的断言**。

仓库根就是你的工作目录，尚未发布。**发布之前请你把它审一遍。**

这套工具的设计规则，作者声称每一条都来自一次真实事故（见 `docs/LESSONS.md`）。
**你的任务有两层：审这个工具能不能用；审它自称的那些保证是不是真的。**

### 0.1 你接手前刚发生的事（重要，这一轮的重心在这里）

**2026-10-02，作者发现这个工具自己的三轮自审是假的。**

三轮的通道配置写着 kimi / qwen / codex 三个来源。实际**三条全部由同一个模型服务**：
两个 `claude-cli` 通道声明的端点与密钥写在**进程环境变量**里，
而 CLI 自己的用户级 settings **盖过了进程环境变量**——那几个变量一次都没生效，
请求被送进本机代理，由它按自己的 provider 路由。三个「独立来源」从来就不存在。

- 更正记录：`reviews/CORRECTIONS.md`（**这是本轮的重点审计对象之一，见 §2.F**）
- 已做的机制补丁：`quorum/preflight.py`（**从未被任何人审过，见 §2.G**）

作者对这件事的定性是：**「这不是审核员不认真，是这一项从来没在射程里」**——
`CONTRACT.md` 把 `vendor` 定义为**声明**，工具不去核实，于是恰好是偏掉的那一轴没有任何检查。

**作者的这个自我诊断本身也是可证伪的。** 请审它。

## 2. 审计线

### A. 契约 ↔ 实现：逐条复验作者的声明

1. **「审核员只读、结论由 runner 落盘」**——审核员进程有没有任何路径能写被审材料？
2. **「内容优先于退出码」**——`gates.evaluate` 的四道门能否被一份**空洞但形式合规**的产出骗过？
3. **「结论先写临时文件、已有非空结论先留档、原子落位」**——有没有哪个分支会原地覆盖或截断已有结论？
4. **「密钥不进配置、不进命令行」**——真的吗？`ANTHROPIC_AUTH_TOKEN` 最终出现在哪些地方
   （argv / env / 磁盘）？`ps` 能看到什么？
5. **「材料快照指纹」**——它对 `sources` 的计算是否**真的**能发现材料变化？
   大文件只按 (大小, mtime) 计入的取舍，会不会在真实场景里静默失效？`snapshot_exclude` 的匹配有没有洞？
6. **「同 vendor 不得有两个 primary」**——只靠 `load()` 一处校验够吗？还有别的入口能绕开吗？
7. **「plate 只解析表头含『严重度』的表」**——审核员换个表头写法会怎样？解析失败是静默的还是可见的？
8. **「verify 抓台账说谎」**——判定四档（说谎 / 未更新 / 无断言 / 一致）的语义对不对？
   默认（非 `--strict`）下，一份**所有行都没填 check** 的台账退出码是多少？这合理吗？
9. **「通道声明与事实分开」**——`vendor` 是声明、`harness` 是事实。还有哪些字段是**声明**，
   而读者会当成事实？逐个列出来。

### B. 交叉表本身：对齐算法能被怎么打脸

这是这个工具的核心，也是作者最没把握的地方。作者自称：

> 对齐是**启发式**的（IDF 加权词重叠，同文件降门槛），刻意保守——宁可拆细，不要合错。

请你**攻击这个说法**：

- 造两组反例：**该合的没合**（同一件事被拆成多簇）、**不该合的合了**（两件不相干的事进了一簇）。
  阈值在 `quorum/plate.py` 的 `cluster()` 里，可以直接调它做实验。
- 更重要的：**当一簇里混进一条错的时候会发生什么？**
  `demo/canned/gamma.md` 里那条 🔴 是作者**故意写错**的（症状对、归因错）。
  它现在会被合进「跨模型族一致」那一簇吗？汇总表会不会因此给出误导性的置信度？
  细节里「逐条列原话」这个缓解措施，够不够？
- 同一家的两条**永远不会**合并——这个规则在什么情况下是错的？
- **N=2 时的交叉表是什么样？** 只有两个审核员时，「一致」和「独有」还能区分什么？
  `plate` 有没有在只有两家时给出读者会误解的标签？

### C. 反驳作者的方法学结论

作者的核心论断是：

> **门禁检查的是「它自己定义的那个性质」，不是「读者以为的那个性质」。绿灯是真的，但它证明的不是你以为的事。**

作者说这是从多次真实事故里提炼的，并声称 quorum 的设计就是为了对付它。
**你的任务：在 quorum 自己身上找反例。** 这个工具里有哪些检查/断言/保证，
同样在检查「作者定义的性质」而不是「用户以为的性质」？

逐条列出来。这一节是本轮最有价值的增量之一。

### D. 反向证伪

1. **`docs/LESSONS.md` 里的事故是真的吗？** 对着代码看：那些规则真的对应那些事故，
   还是「事后给规则编了个故事」？
2. **demo 的三个事故**是否真能复现（不是靠注释声称）？第三个（`PYTHONHASHSEED`）你亲自跑两个种子验证。
3. **测试有没有「永远为真」的断言**？找出任何一条**不可能失败**的测试或 assert。
   包括 `quorum preflight --self-test`：它声称四档都能落到位——**这四个用例真的各自只能落在它那一档吗？**
   （作者承认自己在这里踩过一次：第一版预检只有阴性对照，而真实 CLI 对坏凭据是**挂住**不是报错，
   于是「被拒」和「通道是死的」混成同一档，死通道会被报成「已核实」。）
4. **`check-leaks` 能不能被绕过**？构造一份含泄漏的文件，看它抓不抓得到；再试着让 `--self-test` 通过而实际失效。
5. **找一条做不到红的检查。** 全仓的断言（`build.sh` 式的总闸、`pytest`、两个 `--self-test`）里，
   有没有哪一条**在回退它的修复之后依然绿着**？找到一条比复述「N 条全绿」有价值得多。

### F. 出处与更正：作者刚做的这次全仓更正，全不全？

作者在得知「三轮自审的三个来源是假的」之后，做了一次全仓更正。**请审这次更正本身。**

1. **更正全不全？** 全仓搜一遍，还有没有别处**仍然**把三个通道说成「三个独立来源」
   （或等价的「跨模型族一致」「不同厂商」「多模型」之类的声明）而没有指向更正记录的地方？
   把每一处列出来。**这是本条的主要产出**——缺一处，那次更正就是半成品。
2. **更正准不准？** `reviews/CORRECTIONS.md` 里的因果链（环境变量被 settings 盖过 →
   请求改道 → 三个通道实为同一模型）站不站得住？有没有**另一种解释**同样能产生观测到的现象，
   而作者没想到？（提示：作者手上有的是本机代理的请求日志，那只记录了经过代理的流量。）
3. **作废的范围划得对不对？** 作者保留了「发现本身」、作废了「置信度」。
   这个切法成立吗？有没有哪条发现，它的**内容**本身依赖于「有多个独立来源」这个前提？
   （比如：靠「两家都说」才敢下的判断、靠交叉才排掉的假阳性。）
4. **`harness` 那一轴作者说「是真的」。** 这个说法对吗？`claude-cli` 与 `codex-cli`
   在那三轮里真的是两个独立的 harness 吗？证据在哪？
