# 每条规则背后的事故

这个工具里没有一条设计是凭空想出来的。以下每条都对应一次真实的翻车——**包括工具自己翻的车**。

---

## 「内容优先于退出码」

**事故**：两个审核员各产出了一份 20+ KB、结构完整、四个必需章节齐全的结论，
却在收尾时收到 `SIGTERM`（`rc=143`），于是被脚本按「失败」处理、改名成 `FAILED`。
与此同时一份 0 字节的空产出会被正确地判失败——**门禁分不清「进程被信号收了」和「模型啥也没说」**。

退出码描述的是进程，不是材料。四道内容门（体积 / 严重度标记 / 必需章节 / 非空）全过就该接受，
`rc` 只记进日志与注记。

## 「结论先写临时文件、已有结论先留档」

**事故**：为了测超时看门狗，我拿真实的审核脚本做了一次演练，把 `qwen` 分支指向了同一份**真实结论**的输出路径。
`> "$OUT"` 在脚本启动的瞬间就把那份 20 KB 的结论**截断成 0 字节**，随后看门狗按失败流程把它改名成了 `FAILED`。

那份结论最后是从会话转录里逐字重建的。**损坏一份已有结论，比不产出更糟**——不产出只是没收获，
损坏是负收获。所以：先写临时文件，四门全过再原子落位；已有非空结论先自动留档。

## 「必须有超时看门狗」

**事故**：一个审核员连接死等，**空跑 5 小时**、0 字节产出、进程还活着。
在外部看来，「审核员挂了」与「审核员还在想」完全一样。

## 「材料快照指纹进结论头部」

**事故**：一个审核员在结论里手写了一段「本结论以 21:38–21:44 的工作区状态为准」——
因为作者在它审计期间一直在改文件。**这句话是对的，但它无法被验证**；
事后没人能判断那份结论到底对应哪一版材料。

现在 `run` 会在开始与结束时各取一次快照指纹，写进结论头部；`plate` 发现各家快照不一致时直接报警。

## 「门禁检查的性质，可能不是读者以为的那个性质」

**事故（三次，同一副骨架）**：

1. **分母静默缩水**：门禁检查「文档里的数字能不能从数据文件算出来」。E0 那行写 51.2%，
   而 51.2 = 21/41 —— 确实能从数据算出来，所以门禁放行。可读者以为那是「100 条上的成绩」。
   门禁问的是「这个数算不算得出来」，读者问的是「这个数是不是这道题的答案」。
2. **门禁绿材料错**：门禁逐字节校验文档里的数字区块，区块一直是对的——区块**外面**的正文被删光了它不知道。
   真因是回填脚本的调用点写成 `open(p, "w").write(replace(p, ...))`：`open(p, "w")` **先截断**，
   函数再去读，读到空文件，于是每次回填都把标记区间之外的正文擦掉。三份对外文档一度只剩数字块。
3. **切分非确定性**：门禁断言「train 与 held-out 没有命令串重叠」（确实是 0）。
   但它没检查「这份数据能不能被重新生成出来」。切分时对一个 `set` 直接 `shuffle`，
   而字符串哈希每进程随机化 —— **同参数重跑会得到不同的数据**。冻结指纹把字节钉死了，
   所以产物看起来是锁定的；但「照文档重跑」给出的是另一个东西。

**共同点**：门禁检查的是**它自己定义的那个性质**，不是**读者以为的那个性质**。
绿灯是真的，但它证明的不是你以为的事。

**所以改法不是「多加几个检查项」**（那是打地鼠），而是：把门禁从「重算数字」升级成
**「重跑发布动作」**——真的跑一遍发布流程，把产出和仓库里的产物逐字节比。
原则一句话：**凡是「我以为脚本是这么做的」的地方，都得有一条能失败的断言。**

## 「自检的 pattern 必须从规则表派生」

**事故**：一个项目的脱敏自检只查三类形态（IP / 绝对路径 / 云厂商密钥前缀），
比它自己的脱敏规则少了四类。于是它对着一份含 585 处本机用户名的文件打印：

```
脱敏残留: 无 ✓
```

**一句读起来像「已验证」的输出**，实际只验了子集。

对应地，`quorum check-leaks --self-test` 会给每条规则**种一个样本**并断言它能被抓到——
**自检本身必须能失败**。一份不能失败的检查不是检查，是装饰。

## 「审核员的结论是断言，不是事实」

**事故**：一个审核员断言「在役权重其实是上一版」，语气肯定、给了命令、给了字节数。
**它是错的**——它拼接的是仓库里一份历史下载残留（上一版的分片），而不是在役权重。
是另一个审核员用逐字节 `cmp` 把它推翻的。

同一轮里还发生了反向的事：另一个审核员的一条 🔴 也被证实站不住。

所以交叉表分三档，且明细**逐条列出各家的原话**——同一处发现，各家的归因可能相反
（一个说「分母算错了」，另一个说「文件被人换过了」）。合并只说明「说的是同一处」。

## 「处置台账的 ✅ 需要断言，否则它就是一句话」

**事故**：一份 22 条的外部复核处置台账，全部标 ✅。下一轮复核专门去审这些 ✅，
结果相当一部分站不住。**没有任何东西验证过它们。**

这就是 `quorum verify` 存在的理由：`check` 跑不过的 ✅，是台账在说谎。

## 「工具保护了你，不代表你保护了自己」

**事故**：runner 里写了完整的结论保护（已有非空结论先留档、先写临时文件再原子落位），
测试也覆盖了这条。然后我用一条 shell 命令把第二轮的原始结论覆盖掉了：

```bash
mv reviews/out/*.md reviews/out/round2/     # 与第三轮同名 → 直接覆盖，没有留档
```

**保护写在工具里，绕过它的路径写在工具外。** 那条 `mv` 不在任何门禁的管辖范围内，
也没有任何东西会提醒我「你要覆盖的这几份是非空结论」。

教训：当一件事很重要时，保护不能只做在「正规路径」上——**绕过路径才是它真正被绕过的地方**。

## 「门禁的结果不该取决于跑它的机器」

**事故**：`check-leaks` 有一条规则是「材料里出现本机用户名」。本机跑全绿，推到 GitHub 之后
**CI 挂了** —— 因为 GitHub Actions 上的用户名恰好是 `runner`，于是它把代码和文档里
所有英文单词 "runner" 都报成了泄漏。

这一条比「误报」更值得记：**同一个仓库、同一份规则，换个机器结论就变了**。
一个会随环境翻转的门禁，比没有门禁更糟——你会先学会不信任它。

改法不是加白名单，而是**把规则写对**：要防的泄漏本来就是「**路径里**出现本机用户名」，
锚成 `[/~]name/` 之后，同名词不再误报，规则也不再依赖环境。

（附带一句：这条是 CI 抓到的，不是我自己发现的。**把门禁放到另一台机器上跑，本身就是一种审计。**）

---

## 一句话总结

> 这个工具不保证审核员是对的，它保证的是：**你没有办法在没验证过的情况下宣称某件事是对的而不被发现。**
