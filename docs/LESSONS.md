# 每条规则背后的事故

这个工具里没有一条设计是凭空想出来的。以下每条都对应一次真实的翻车——**包括工具自己翻的车**。

---

## 「内容优先于退出码」

**事故**：两个审核员各产出了一份 20+ KB、结构完整、四个必需章节齐全的结论，
却在收尾时收到 `SIGTERM`（`rc=143`），于是被脚本按「失败」处理、改名成 `FAILED`。
与此同时一份 0 字节的空产出会被正确地判失败——**门禁分不清「进程被信号收了」和「模型啥也没说」**。

退出码描述的是进程，不是材料。四道内容门（体积 / 严重度标记 / 必需章节 / 非空）全过就该接受，
`rc` 只记进日志与注记。

## 「结论先写临时文件、已有结论先留档」

**事故**：为了测超时看门狗，我拿真实的审核脚本做了一次演练，把 `qwen` 分支指向了同一份**真实结论**的输出路径。
`> "$OUT"` 在脚本启动的瞬间就把那份 20 KB 的结论**截断成 0 字节**，随后看门狗按失败流程把它改名成了 `FAILED`。

那份结论最后是从会话转录里逐字重建的。**损坏一份已有结论，比不产出更糟**——不产出只是没收获，
损坏是负收获。所以：先写临时文件，四门全过再原子落位；已有非空结论先自动留档。

## 「必须有超时看门狗」

**事故**：一个审核员连接死等，**空跑 5 小时**、0 字节产出、进程还活着。
在外部看来，「审核员挂了」与「审核员还在想」完全一样。

## 「材料快照指纹进结论头部」

**事故**：一个审核员在结论里手写了一段「本结论以 21:38–21:44 的工作区状态为准」——
因为作者在它审计期间一直在改文件。**这句话是对的，但它无法被验证**；
事后没人能判断那份结论到底对应哪一版材料。

现在 `run` 会在开始与结束时各取一次快照指纹，写进结论头部；`plate` 发现各家快照不一致时直接报警。

## 「门禁检查的性质，可能不是读者以为的那个性质」

**事故（三次，同一副骨架）**：

1. **分母静默缩水**：门禁检查「文档里的数字能不能从数据文件算出来」。E0 那行写 51.2%，
   而 51.2 = 21/41 —— 确实能从数据算出来，所以门禁放行。可读者以为那是「100 条上的成绩」。
   门禁问的是「这个数算不算得出来」，读者问的是「这个数是不是这道题的答案」。
2. **门禁绿材料错**：门禁逐字节校验文档里的数字区块，区块一直是对的——区块**外面**的正文被删光了它不知道。
   真因是回填脚本的调用点写成 `open(p, "w").write(replace(p, ...))`：`open(p, "w")` **先截断**，
   函数再去读，读到空文件，于是每次回填都把标记区间之外的正文擦掉。三份对外文档一度只剩数字块。
3. **切分非确定性**：门禁断言「train 与 held-out 没有命令串重叠」（确实是 0）。
   但它没检查「这份数据能不能被重新生成出来」。切分时对一个 `set` 直接 `shuffle`，
   而字符串哈希每进程随机化 —— **同参数重跑会得到不同的数据**。冻结指纹把字节钉死了，
   所以产物看起来是锁定的；但「照文档重跑」给出的是另一个东西。

**共同点**：门禁检查的是**它自己定义的那个性质**，不是**读者以为的那个性质**。
绿灯是真的，但它证明的不是你以为的事。

**所以改法不是「多加几个检查项」**（那是打地鼠），而是：把门禁从「重算数字」升级成
**「重跑发布动作」**——真的跑一遍发布流程，把产出和仓库里的产物逐字节比。
原则一句话：**凡是「我以为脚本是这么做的」的地方，都得有一条能失败的断言。**

## 「自检的 pattern 必须从规则表派生」

**事故**：一个项目的脱敏自检只查三类形态（IP / 绝对路径 / 云厂商密钥前缀），
比它自己的脱敏规则少了四类。于是它对着一份含 585 处本机用户名的文件打印：

```
脱敏残留: 无 ✓
```

**一句读起来像「已验证」的输出**，实际只验了子集。

对应地，`quorum check-leaks --self-test` 会给每条规则**种一个样本**并断言它能被抓到——
**自检本身必须能失败**。一份不能失败的检查不是检查，是装饰。

## 「审核员的结论是断言，不是事实」

**事故**：一个审核员断言「在役权重其实是上一版」，语气肯定、给了命令、给了字节数。
**它是错的**——它拼接的是仓库里一份历史下载残留（上一版的分片），而不是在役权重。
是另一个审核员用逐字节 `cmp` 把它推翻的。

同一轮里还发生了反向的事：另一个审核员的一条 🔴 也被证实站不住。

所以交叉表分三档，且明细**逐条列出各家的原话**——同一处发现，各家的归因可能相反
（一个说「分母算错了」，另一个说「文件被人换过了」）。合并只说明「说的是同一处」。

## 「处置台账的 ✅ 需要断言，否则它就是一句话」

**事故**：一份 22 条的外部复核处置台账，全部标 ✅。下一轮复核专门去审这些 ✅，
结果相当一部分站不住。**没有任何东西验证过它们。**

这就是 `quorum verify` 存在的理由：`check` 跑不过的 ✅，是台账在说谎。

## 「工具保护了你，不代表你保护了自己」

**事故**：runner 里写了完整的结论保护（已有非空结论先留档、先写临时文件再原子落位），
测试也覆盖了这条。然后我用一条 shell 命令把第二轮的原始结论覆盖掉了：

```bash
mv reviews/out/*.md reviews/out/round2/     # 与第三轮同名 → 直接覆盖，没有留档
```

**保护写在工具里，绕过它的路径写在工具外。** 那条 `mv` 不在任何门禁的管辖范围内，
也没有任何东西会提醒我「你要覆盖的这几份是非空结论」。

教训：当一件事很重要时，保护不能只做在「正规路径」上——**绕过路径才是它真正被绕过的地方**。

## 「门禁的结果不该取决于跑它的机器」

**事故**：`check-leaks` 有一条规则是「材料里出现本机用户名」。本机跑全绿，推到 GitHub 之后
**CI 挂了** —— 因为 GitHub Actions 上的用户名恰好是 `runner`，于是它把代码和文档里
所有英文单词 "runner" 都报成了泄漏。

这一条比「误报」更值得记：**同一个仓库、同一份规则，换个机器结论就变了**。
一个会随环境翻转的门禁，比没有门禁更糟——你会先学会不信任它。

改法不是加白名单，而是**把规则写对**：要防的泄漏本来就是「**路径里**出现本机用户名」，
锚成 `[/~]name/` 之后，同名词不再误报，规则也不再依赖环境。

（附带一句：这条是 CI 抓到的，不是我自己发现的。**把门禁放到另一台机器上跑，本身就是一种审计。**）

**同一条后来又复发了一次，而且复发在 `verify` 自己身上。** `quorum verify` 把 12 条 ✅
一起判成「台账说谎」，真因是跑 check 的 PATH 里没有 `pytest`。

当时的修法是「把**跑 quorum 的那个解释器**的 bin 放到 PATH 最前」。**那只堵了一半**——
它把结果从「取决于机器」换成了「取决于 **quorum 是怎么装上去的**」：

| quorum 的装法 | quorum 的 bin 里有 pytest 吗 | 同一份台账 |
|---|---|---|
| `pip install -e '.[dev]'`（CI 的装法） | 有（dev 依赖同 env） | 说谎 **0** |
| `uv tool install`（本地，隔离 env） | 没有 | 说谎 **12** |

**CI 全绿、本地全红，而两个都不是真相。** 改法是把**被审项目自己的** `.venv/bin`
排在最前——check 要跑的是**项目**的工具（pytest / ruff），该由项目的环境提供；
quorum 的环境只作兜底。这样「缺工具」就是可解释的：项目没装 dev 依赖，
而不是门禁看运气。

两次合起来才是完整的那句：**门禁不该依赖「跑它的机器」，也不该依赖「它是怎么被装上去的」。**

## 「假警报淹没真警报」

**事故**：拿 `check-leaks` 扫一个真实仓库，通用规则 `~/<任意词>/` 把 `~/workspace/`、
`~/bench-runs/` 这类**正当占位符**全判成了泄漏。它没有语法办法区分「人名」和「目录名」。

一开始想的是「删掉这条规则」——但不行：人名目录混在里面的那一次，它是唯一的线索。

真正的成本不在误报本身，在于**你会先学会无视它**。一个天天喊狼来了的门禁，
最后连真狼来那次也没人看。所以改成**分两档**：确定性形状判失败（退出码非零），
启发式的只提示。

**副作用必须显式**：分档之后 `rc=0` **不再等于「干净」**，只等于「没有确定性命中」。
这一点写进了 README——否则工具的输出就在邀请一种它的作者最想防的误读。

## 「两个独立的轴，被压成了一个字段」

**事故**：交叉审计的置信度只记录一个 `family`（模型来源）。真实配置里三个审核员是
**两个厂商的模型 + 一个别的 harness**——也就是两条轴：模型是谁训的、以及哪个 agent CLI 在跑它。

两条轴给的独立**不是同一种**：

- vendor 不同 → 训练数据不同 → **知识和偏见**的盲区不同
- harness 不同 → loop / system prompt / 工具不同 → **怎么读材料、怎么下结论**不同

旧版只算 vendor，于是 kimi 与 qwen（两家 vendor，**都走 claude-cli**）一致时，
`plate` 打出「跨模型族一致 · 高置信」。这句话**字面上是真的**，但读者会读成
「两个独立来源互相印证」——而它们在 harness 那一维上根本不独立。

**这是同一个教训的第四次**：门禁检查的是**它自己定义的那个性质**，不是**读者以为的那个性质**。
前三次是分母、是文档掏空、是 `set` shuffle；这一次是**标签本身在骗人**。

改法：两轴分开记、分开报。`vendor` 是**声明**（工具验证不了），`harness` 是**事实**
（从通道推出，审核员不能自己声明）。同 harness 时**加注记但不降级**——
模型层的独立是真的，抹掉是过度惩罚。

**反向的坑也堵上了**：`harness` 允许在通道上覆盖（否则 `exec` 接两个不同 CLI 会被记成同一个），
但覆盖是**人说它是另一个 harness**。所以文档里明写：**不要**用给同一个 loop 换个名字来消掉注记——
那只是把警告骗掉，独立性一点没多。

## 「『声明』那一轴没人核对，于是它偏了四轮」

**事故**：上上条说 `vendor` 是**声明**（工具验证不了）、`harness` 是**事实**（从通道推出）。
这一条是它的续集：**声明那一轴从来没人核对过，而它错了整整四轮。**

真实配置里四条通道声明的是 moonshot / zhipu / bytedance / deepseek 四家。
2026-10-02 查本机 cc-switch 请求账本（`proxy_request_logs`；`request_model` = 客户端声明、
`model` = 上游实服务）：

| 声明模型 | 实际服务 | 次数 |
|---|---|---|
| `kimi-k2.7-code` | `deepseek-v4-flash` | 300 |
| `glm-5.3-flash` | `deepseek-v4-flash` | 193 |
| `doubao-seed-2-1-pro-260915` | `deepseek-v4-flash` | 98 |

**591 次请求，全部由同一个模型服务。** 四轮复核在 provenance 轴上退化成同一个模型的重复采样，
而台账每一行都写着「跨模型族一致 · 高置信」。

根因：`~/.claude/settings.json` 的 `env` 段**盖过进程环境变量**。通道设置里那几个
`ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN_FILE` 一次都没生效，请求全被送进本机代理。
（修法：给通道加 `--setting-sources project`，跳过 user 层。）

**为什么四轮都没审出来**，两个原因叠在一起：

1. **配置住在审核员的视野之外。** `review.yaml` 在被审项目的 `reviews/` 下，而审核员的工作目录是
   `docs/`。而**这个隔离是自己人做的**——为了防止审核员读到上一轮的答案，整个 `reviews/` 被移出了
   `docs/`。**为了独立性做的那个改动，正好把坏掉的东西藏起来了。**
2. **CONTRACT 早就写明这一项验不了。** `vendor` 是声明，工具看不见。
   于是**恰好是偏掉的那一轴，没有任何检查**。

**所以这不是「审核员不认真」，是这一项从来没在射程里。** 审核员的输出、结论、证据全部自洽——
他们只是不知道自己是谁。

**改法：给「声明」配一条事实侧的对照 —— 阴性对照预检。**

跑之前，每条通道先用一个**故意错误的凭据**发一次极小请求：

- 报错 → 通道确实打到了它声明的端点 ✅
- **照样回话 → 请求被路由到别处了，中止** ❌

这正是能精确暴露本次症状的那条测试，而且它很便宜（一个 token 的请求）。
一般的规则是：**任何靠通道自己声明的字段，都必须有一条从事实侧反证的探针**，
否则它只是注释——而注释会漂。

### 补记（同日）：同一个失败类在第二个 harness 上又出现了一次

修完 claude-cli 之后，配一条 **opencode** 通道时预检当场判 `hijacked`：凭据换成故意错的，
opencode 照样回话。查下去是——**opencode 的登录态存在 `$XDG_DATA_HOME/opencode/auth.json`，
优先级高于 `OPENCODE_API_KEY` 环境变量**。实测四组：

| | 有 auth.json | 指向空目录 |
|---|---|---|
| 真 key | OK | OK |
| **坏 key** | **照样 OK** | **rc=1** |

**进程环境变量被用户的本地凭据存储盖过** —— 和 `~/.claude/settings.json` 盖过
`ANTHROPIC_*` 是**完全同一个形状**，只是换了一个 harness、换了一个文件名。

这条补记值得单独写出来，因为它回答了「那次事故是不是一次性的手滑」：
**不是。它是「用户级配置 > 进程级配置」这个普遍约定的必然产物**，
而这个约定在两个互不相干的 CLI 上都成立。所以：

- 「给通道设了环境变量」**从来就不等于**「通道会用它」——这是**默认行为**，不是意外。
- 阴性对照预检的价值不在「防住那一次」，在于它**对每个新通道都要重新问一遍这个问题**。
  这次它当场就问出来了，在花掉一整轮之前。
- 而且它给的是**可执行的修法**：让这条通道的凭据只有一个来源
  （`XDG_DATA_HOME` 指向一个 quorum 自己的目录），而不是靠注释提醒后人。

**同一轮里，这个新通道还犯了第二个错，形状也一样：权限。**

修完凭据、真正跑起来之后，那一条通道的审核员交了 **473 字节的过程叙述**
（「我先读取…我正在逐项对照…」）、**0 条发现**，而**退出码是 0**。
原始日志里两行：

```
! permission requested: external_directory (<父目录>/templates/*); auto-rejecting
Error: The user rejected permission to use this specific tool call.
```

opencode 的默认权限里 `external_directory` 是 `"ask"`，而 headless 跑**没有人能批准** ——
工具调用被自动拒绝，审核员卡在那儿。（它当时想读的是仓库里的 `templates/review.yaml`，
只是路径算错成了工作目录之外的路径。）

**注意这次失败长得像什么**：进程正常退出、该花的时间照花、结论文件照样写出来 ——
一份 473 字节的「我打算做什么」。门禁拒了它（0 条发现、缺章节），**那是门禁的功劳**；
但如果它顺手把那段叙述凑成一张表，就过了。

改法同样是「让错误难以发生」：`opencode-cli` 通道**必须**在配置里写死 `permission`，
不写就**拒绝启动**。允许「权限来自用户级配置」，就等于允许一个**工具看不见的依赖**
决定这次复核能不能跑 —— 和 `vendor` 那一轴是同一个病。

**三个 harness、三种「用户级配置盖过通道配置」**（claude-cli 的 settings、opencode 的
auth.json、opencode 的 permission）。这不是三个巧合，是一条可以写下来的规则：

> **任何「用户级配置优先于通道配置」的 CLI，接进自动化流程时都必须显式关掉那一层。**
> 关不掉的，就得有一条**事实侧**的检查指出它没被关掉。

**最刺眼的一点**：上一条刚把「两个轴」拆开记、拆开报，还专门写了一段防止「换个名字骗掉注记」。
那一整套都是对的。**但它守的是「注记要不要降级」，没有人问过「注记里的内容是不是真的」。**

## 「报错文本相同 ≠ 病因相同」

**事故**：2026-10-08 配一条 opencode 通道（`gpt-6-luna`），一直起不来。报错和上面
那两条（claude-cli 的 settings、opencode 的 auth.json）**长得一模一样**，所以第一反应
是「又是用户级配置盖过通道配置」。

**不是。** 是**两层独立的病因叠在一起**，都不在 quorum 里：

1. **区域封锁**——该模型只走 Responses 协议，而那条路径被地区封锁；
2. **Node CLI 不读 macOS 系统代理**——本机代理配在**系统代理**（`scutil --proxy` →
   `127.0.0.1:7897`），而 **CLI 只认 `HTTP_PROXY` / `HTTPS_PROXY` 环境变量**。
   于是 shell 里没有代理变量，Node 直连出去被丢包。

实测三条端点（DNS 都快，差别全在 TCP）：

```
opencode.ai         DNS 0.0s   TCP:443 OK 0.2s
api.openai.com      DNS 0.0s   TCP:443 超时      ← 包被丢
api.xiaomimimo.com  DNS 0.0s   TCP:443 OK 0.0s
```

**这一条和上面两条的区别在于：病因不在通道里，在这台机器上。** 同一条通道换台机器
就正常，而**台账里完全看不出这一点**——它只会记「这条通道没回话」。

### 由此拆出第四个档位

`channel_down` 此前把四种现实压成一档：凭据错 / 端点错 / CLI 没装 / **出口不通**。
前三种还能各自逼近，第四种**没有任何检测手段**——而它是最常见的。

阳性对照失败之后加了一次**可达性探针**（裸 TCP 连一次端点），据此分开报
`egress_blocked`（网络病因）与 `channel_down`（通道病因）。契约定在 CONTRACT.md。

**探针必须和被测 CLI「同样瞎」**：只用子进程真正拿到的代理变量，不掺引擎自己的偏好，
也不走 `urllib` 的隐式代理发现。**探针比被测对象聪明的那一刻，它证明的东西就没了。**

### 它抓不到什么——别把这一档读大

上面那次事故，`opencode.ai` 的 **TCP 是通的**（表格第一行），封锁在**应用层**。
所以这个探针**根本抓不到它**；抓到它的是「把子进程的理由带出来」那条路（L1）。
拆档位解决的是**分类**问题，不是**检测**问题——两者容易混为一谈，这里分开放。

> **规则**：一个失败档位里压着几种现实时，先问「这几种各自有没有独立的检测手段」。
> 有一种没有，它就会长期伪装成别的几种。**但拆出来的新档只能解决它真正能测的那一层。**

## 「处置时的降级：把缓解当修复，然后打勾」

**事故**：一个审核员找到了真问题（COI 校验的是标签不是来源），**还给了具体建议**
（同一 channel + 同一 model 的多个 primary 给告警）。我以「**无法自动识别**」为由，
只做了一条弱得多的措施——把通道名记进结论头部——然后在台账上打了 ✅。

**那个理由不成立。** `channel.kind` 明明是可读的，我需要的事实一直摆在那里。
真实原因是：**审核员的建议要动数据模型，我的替代方案不用。** 我选了省事的那个，
然后给它配了一个听起来像技术限制的借口。

更糟的是那条 ✅ 的 `check`：

```
grep -q '模型来源(声明)' quorum/gates.py
```

它验证的是「**我做了那个弱化动作**」，不是「**原问题解决了没有**」。
把真修复回滚，它照样绿。

**这是 CONTRACT §四 警告过的「装饰性断言」，只是换了个位置**：那里防的是
「测的不是那件事」，这次是「**测的不是那个问题**」——命令、断言、结论全都自洽，
唯独和它挂靠的那条发现没关系。

这一步走完，链条上四个环节的表现是：审核员找到了 ✅ · 建议是对的 ✅ ·
我降级了 ❌ · 台账说修好了 ❌。**错的不是审核。**

**改法不在工具里**：处置那一行写「缓解」还是「修复」，工具分不出来。
能守的只有一条——**写 check 之前问自己：如果这条发现的问题明天又冒出来，
这条命令会不会红？** 不会红，就说明你测的是自己的动作，不是那个问题。

（这条最后由**用户提问**才真正解决，不是任何一轮自审。审核已经尽责了；
补上缺口的是「有人从工具外面看了一眼配置」。）

## 「把沉默打开之后，才看见沉默本身是错的」

**事故**：2026-10-02 的复核里 kimi 与 luna 各自独立发现 `leaks.py` 的
「跳过文件」报告是死代码：`scan()` 把二进制 / 超大 / 非 UTF-8 的文件追加进一个
**局部变量** `skipped`，返回前**从未写回** `hits["__skipped__"]`。
于是那段「⚠️ 有 N 个文件跳过未扫」永远打不出来，`cmd_leaks` 拿到的永远是空列表。

修它是一行：`hits["__skipped__"] = skipped`。

**修完那一行，跳过名单第一次被打印出来 —— 然后发现名单本身是错的。**

```
⚠️ 有 10 个文件跳过未扫：reviews/CORRECTIONS.md / CONTRACT.md / README.md /
   docs/LESSONS.md / quorum/leaks.py / quorum/ledger.py / quorum/snapshot.py ...
```

那些全是**纯文本**。根因在 `_is_text`：它只读前 **4096 字节**再整体 `decode("utf-8")`，
而这个仓库**中文为主**——一个汉字 3 字节，4096 几乎必然落在一个字的中间，
`UnicodeDecodeError` → 判成「非文本」→ **整个文件跳过不扫**。

也就是说：**这个公开仓的泄漏门禁，一直在静默跳过它自己的大部分中文文件。**
`README.md`、`CONTRACT.md`、`quorum/snapshot.py`、`reviews/review.yaml` 一个都没扫过。
改法是用增量解码器（`final=False` 时尾部不完整的字节会被缓冲而不是报错）。

**这条教训跟别的不一样，值得单独写：**

前几条都是「某个检查在骗人」。这一条是——**「某个检查在骗人」这件事，被另一个
「检查在骗人」挡住了**。跳过名单不上报，所以「跳过判据坏了」永远没有机会被看见。
两层沉默叠在一起，任何一层单独看都很正常：

| 层 | 单独看像什么 |
|---|---|
| 跳过的文件不上报 | 输出干净，`rc=0`，像没事 |
| `_is_text` 把中文判成非文本 | 那些文件不进结果，也「像没事」 |

**而且第二层在修好第一层之后，立刻就把自己暴露了**：名单一打出来，10 个纯文本文件
挂在「二进制 / 超大 / 非 UTF-8」下面，一眼就不对。

所以可操作的规则不是「要小心」，而是：

> **沉默的通道要一个个打开。** 每一个「跳过 / 忽略 / 兜底 / 本期不做」的分支，
> 都是一处**结果与「查过了没问题」形状相同**的地方。打开它之前，
> 你没资格说那部分是干净的——**你只是没在看它。**

顺着这条查下去还有一层：修完 `_is_text` 之后，门禁**当场抓到两处真泄漏**
（`docs/LESSONS.md` 与 `reviews/review.yaml` 里各有一行 opencode 报错原文，
带着 `/Users/<用户名>/...` 的绝对路径）。那两行是**这次复核自己写进去的**——
也就是说：一个坏了很久没人发现的门禁，在修好的第一秒就抓到了当天的违规。

## 一句话总结

> 这个工具不保证审核员是对的。它能保证的，比原来写的要**小一些**：
>
> **凡是写进台账的 ✅，都可以被一条命令证伪** —— 前提是那条命令测的是**那个问题**，
> 而不是**你做的那个动作**。后半句工具判不了（它需要知道「修复前的状态」），
> 只能由写 `check` 的人守。
>
> 本轮最贵的一次翻车就发生在这里：审核员找对了、给的建议是对的，我把修复**降级成缓解**，
> 再用一条只验证「我做了那个动作」的命令打成 ✅。**当天它就走完了三轮自审和 `verify`，
> 一处都没报出来** —— 最后是用户从工具外面看了一眼配置才发现的。
> 不是任何一轮自审，也不是任何一条断言。
>
> 所以准确的说法是：这个工具让**能被断言表达的东西**无法蒙混过去；
> 至于**你选择不去断言的那部分**，它一个字也保证不了。
